在理解了 **PM 對根目錄架構的硬性規範（Sprint-0 延續下來的標準）** 後，我們知道根目錄必須維持 `data-collection/`、`dev/`、`training/`、`documentation/` 等核心資料夾。

在這個硬性約束下，**以資深工程師與架構師的角度來看，依然存在檔案放置錯位與模組耦合的問題**。我們可以在**不變動根目錄名稱**的前提下，對內部層級與依賴關係進行優化。

以下是針對 PM 基礎目錄架構下的**問題盤點**與**內部優化方案評估**：

---

## 一、 PM 基礎目錄架構下的「檔案/資料夾錯位」分析

### 1. `dev/` 內部的業務代碼與模型架構（Code）依賴 `training/`
* **現狀**：為了讀取 BiSeNet 模型架構，`dev/app/face_parsing_bisenet.py` 等生產代碼必須在 runtime 執行 `sys.path.insert(0, str(TRAINING_DIR))`，以便導入 `training/models/model.py` 的程式碼。
* **問題點**：
  * **定義偏離**：PM 定義的 `training/` 是 **「產出模型與訓練結果目錄」**（例如 `.pth` / `.h5` 權重檔），它應該是一個 **Artifacts（產出物）** 資料夾。但現在，FastAPI 卻需要去該目錄下載入 **Python 代碼**。
  * **部署困境**：這使得 `dev/app/` 與 `training/` 產生了強代碼耦合。在 Docker 部署時，如果排除大體積的訓練目錄 `training/`，FastAPI 服務就會因為找不到模型定義程式碼而無法啟動。
* **優化方案**：把模型定義的 Python 代碼（如 BiSeNet 結構）移入 `dev/app/models/`，讓 `training/` 成為純粹的「權重與訓練紀錄輸出目錄」。

### 2. `data-collection/makeup_products/` 放置不當
* **現狀**：此目錄存放的是用於「化妝品推薦系統」的 Concealer 與 Primer CSV/JSON 對照表。
* **問題點**：PM 定義的 `data-collection/` 是 **「資料收集與儲存目錄」**，此專案中其餘子目錄（如 `melasma`, `vitiligo` 等）都是 ML 模型訓練用的病灶圖像數據集。化妝品推薦產品資料屬於**應用程式的業務靜態數據**，放在這裡會造成「影像數據集」與「業務資料庫數據」混雜。
* **優化方案**：將化妝品資料移到 `dev/app/recommendations/data/`，使 `data-collection/` 保持純淨的 AI 訓練圖像數據。

### 3. 開發/測試腳本散落於 `data-collection/scripts/`
* **現狀**：用於離線測試 BiSeNet 分割、RGB 估算等腳本被放在了 `data-collection/scripts/`。
* **問題點**：PM 定義 `dev/` 為 **「開發與執行腳本目錄」**。這些前處理與測試腳本顯然屬於 `dev` 的範疇，而非資料收集。
* **優化方案**：將這些離線腳本統一歸檔到 `dev/scripts/` 底下。

### 4. 模型權重重複與路徑混亂
* **現狀**：人臉偵測模型 `blaze_face_short_range.tflite` 同時存在於 `dev/app/models/` 與 `training/models/`。
* **問題點**：缺乏單一真值來源（Single Source of Truth），增加維護成本。

## 二、 尊重 PM 規範下的「資料夾結構優化方案」

在**不改變根目錄資料夾命名**的前提下，我們對**內部目錄結構**與**程式碼導入邏輯**進行精細化重構：

### 2. 優化方案效益評估

1. **代碼（Code）與權重（Weights）分離**
   * **調整**：將 `BiSeNet` 的 PyTorch 模型定義程式碼移入 `dev/app/models/bisenet.py`；將訓練產出的 `.pth` 權重保留在 `training/checkpoints/`。
   * **效益**：
     1. **移除動態 Path 注入**：移除 `sys.path.insert`，改用乾淨的標準導入 `from app.models.bisenet import BiSeNet`。
     2. **Docker 部署友善**：FastAPI 生產服務的程式碼不再依賴整個 `training/` 資料夾。Docker 部署時可以安全地在 `.dockerignore` 中排除 `data-collection/` 與 `training/` 中的訓練代碼，只需以掛載（Volume）或單獨拷貝方式將 `training/checkpoints/` 權重放入容器即可。

2. **`dev/` 目錄的職責重組**
   * **調整**：在 `dev/` 下劃分 `dev/scripts/`（存放離線評估、RGB 計算等開發腳本）與 `dev/app/`（核心生產服務）。
   * **效益**：完全貼合 PM 最初定義 `dev/` 為「開發與執行腳本目錄」的構想，同時也能將日漸龐大、規範化的 FastAPI 專案安全歸檔，實現開發腳本與生產服務的分離。

3. **業務數據（推薦資料庫）定位明確**
   * **調整**：將粉底液等資料庫從 `data-collection` 移動到 `dev/app/recommendations/data/` 底下。
   * **效益**：`data-collection/` 保持純淨，專門存放圖像數據集，避免與業務推薦資料混淆，這在後續轉移給其他數據人員或進行資料庫遷移時更易於維護。
