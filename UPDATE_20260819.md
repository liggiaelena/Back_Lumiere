# Lumière async analysis and recommendation update — 2026-08-19

## Purpose

This update prepares the local presentation deployment for up to ten unfinished photo-analysis jobs while the site is published through Cloudflare Tunnel. Long-running prediction and product-recommendation work no longer holds the upload HTTP request open. The browser submits once, receives an analysis ID, and polls lightweight status endpoints.

The design deliberately targets one local application instance and one Uvicorn worker. It is not a distributed production queue and should not be scaled by starting multiple Uvicorn workers because each process would load a separate copy of the ML models and run its own in-process workers.

## User-visible behavior

1. A user uploads a JPEG, PNG, or WebP image.
2. The server validates the image, reserves a database job, stores the original file, and returns `202 Accepted` immediately.
3. `/analyze/{analysis_id}` displays a spinner, current stage, and queue position while polling the status endpoint.
4. When analysis is ready, the dashboard appears immediately.
5. Product recommendations continue in their own background worker. The recommendation panel shows a spinner and updates when the persisted result is ready.
6. Refreshing `/analyze/{analysis_id}` resumes status polling without requiring login. Anonymous analyses remain accessible by their unguessable 128-bit analysis ID.
7. Logged-in history records load persisted analysis and recommendation results without calling OpenAI again.
8. When ten analyses are unfinished, the next submission receives HTTP 429 with `Retry-After: 20`. Its image is not saved and no job is created.

## Architecture

```text
Browser / mobile phone
        |
        | POST image (once)
        v
FastAPI request layer -----> PostgreSQL analyses row (queued)
        |                             |
        | 202 + analysis_id           | atomic claim with
        v                             | FOR UPDATE SKIP LOCKED
short status polling                  v
                              Analysis workers (2)
                              - local inference slot (1)
                              - region OpenAI slots (3)
                                       |
                                       v
                              persisted analysis result
                                       |
                                       v
                              Recommendation worker (1)
                              - OpenAI web search
                              - Neon fallback
                                       |
                                       v
                              persisted recommendation result
```

Analysis and recommendation use separate worker loops. A recommendation for user A can run while user B is being analyzed. A recommendation for one analysis is only queued after that analysis reaches `ready`, because it depends on the skin profile, condition map, and medical-safety gate.

## Concurrency controls

Defaults are configured in `dev/app/config.py` and can be overridden by environment variables:

```env
MAX_UNFINISHED_ANALYSES=10
ANALYSIS_WORKER_CONCURRENCY=2
OPENAI_REGION_CONCURRENCY=3
RECOMMENDATION_WORKER_CONCURRENCY=1
OPENAI_RECOMMENDATION_LATENCY_OPTIMIZED=true
JOB_POLL_INTERVAL_SECONDS=0.75
JOB_STALE_AFTER_SECONDS=600
UPLOAD_STORAGE_DIR=.runtime/uploads
```

`OPENAI_RECOMMENDATION_LATENCY_OPTIMIZED=true` keeps the configured model,
web search, product count, and structured response schema unchanged while using
`reasoning.effort=none` and low text verbosity. The opt-in live benchmark in
`tests/test_recommendation_latency.py` compares it with the baseline request.

The capacity of ten counts only these analysis states:

```text
uploading + queued + predicting_local + analyzing_regions
```

Completed analyses release capacity even while their recommendations are queued or processing. Recommendation jobs therefore do not prevent a new photo from entering the analysis queue.

Two analysis coroutines may be active so one job can perform local work while another waits for OpenAI. A process-wide semaphore permits only one job in the local model section. MediaPipe, SegFormer, BiSeNet, and the vitiligo gate therefore do not create uncontrolled CPU or model-memory contention. SegFormer now also has explicit model-load and inference locks.

All facial-region OpenAI calls share a process-wide semaphore with a default capacity of three. Each image still has five logical region calls, but at most three calls across all active analyses can be in flight. Recommendations are serialized by their dedicated single worker.

## Analysis state machine

```text
queued
  -> predicting_local
  -> analyzing_regions
  -> ready
```

Terminal error states are `failed`, `cancelled`, and `expired`. The current worker writes `failed` when processing raises an unrecoverable exception. Each claim increments `attempt_count` and records timestamps and heartbeat data.

The recovery worker checks once per minute. A `predicting_local`, `analyzing_regions`, or recommendation `processing` record whose heartbeat is older than `JOB_STALE_AFTER_SECONDS` is returned to its queue when it has fewer than two attempts. This protects jobs left behind by a process crash.

Database transitions include the expected previous status in their `WHERE` clause. Task claims use `FOR UPDATE SKIP LOCKED`, so two worker coroutines cannot claim the same row.

## Recommendation state machine and persistence

```text
queued -> processing -> ready
                     -> fallback_ready
                     -> failed

queued -> blocked
```

`fallback_ready` means live OpenAI web search failed or was skipped and the stored Neon catalogue produced the result. `blocked` means the medical-safety gate prohibited cosmetic recommendations.

Recommendations are stored in `recommendation_jobs`. A unique constraint on:

```text
(analysis_id, exclusions_hash, lang)
```

deduplicates equivalent requests. Reapplying the same allergen selection returns the existing queued, processing, or completed job. A failed job may be put back into `queued` when explicitly requested again. `analyses.active_recommendation_job_id` records which variant the dashboard and history page should display.

GET endpoints never start OpenAI work. Creating or selecting a recommendation variant is a POST operation; subsequent GET operations only read job state or persisted results.

## Original image retention

The original uploaded bytes are retained, as requested for the presentation. Files are stored under `UPLOAD_STORAGE_DIR` with random names. Docker Compose mounts:

```text
./.runtime/uploads:/app/.runtime/uploads
```

The database stores the absolute file path, content type, and byte size. The original image is not placed inside JSONB. No success, failure, cancellation, or scheduled cleanup path currently deletes it.

Existing derived `face_image` and condition overlay data remain in `result_json`, preserving the current dashboard and history behavior.

## Database upgrade

Fresh databases use the updated `db/init.sql`. Existing databases must apply:

```text
db/migrations/20260819_async_analysis_and_recommendations.sql
```

Example:

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 \
  -f db/migrations/20260819_async_analysis_and_recommendations.sql
```

The migration is idempotent:

- it adds task/status columns with `IF NOT EXISTS`;
- existing analysis rows are marked `ready`;
- existing language values are copied from `result_json` when available;
- existing rows receive empty allergen selections and completed timestamps;
- it creates queue indexes and `recommendation_jobs`;
- it does not delete or rewrite existing `result_json` content.

Application startup also executes the same idempotent migration as a schema guard. Applying the SQL explicitly before deployment remains recommended because it surfaces permission or schema problems before the presentation begins.

## API changes

### Submit analysis

```http
POST /api/analyze
Content-Type: multipart/form-data
```

Success:

```http
202 Accepted
```

```json
{
  "id": "ana_<128-bit-random-id>",
  "analysis_status": "queued",
  "analysis_stage": "queued",
  "queue_position": 3,
  "poll_after_seconds": 2
}
```

Queue full:

```http
429 Too Many Requests
Retry-After: 20
```

### Read status

```http
GET /api/analyze/{analysis_id}/status
```

This endpoint returns analysis state, stage, queue position, recommendation job state, errors, and a suggested polling interval. It never executes analysis or recommendation work.

### Read analysis

```http
GET /api/analyze/{analysis_id}
```

Queued records return their current status and an otherwise empty result. The frontend normally calls this endpoint after status becomes `ready`. When an active recommendation exists, its persisted result and metadata are merged into the frontend-compatible response.

### Request a recommendation variant

```http
POST /api/analyze/{analysis_id}/recommendations
Content-Type: application/json
```

```json
{
  "excluded_allergens": ["fragrance", "lanolin"],
  "lang": "en",
  "force_fallback": false
}
```

This creates or reuses a deduplicated recommendation job. It does not wait for OpenAI.

### Read recommendation state/result

```http
GET /api/recommendation-jobs/{job_id}/status
GET /api/analyze/{analysis_id}/recommendations
```

The legacy singular read route remains as a read-only alias:

```http
GET /api/analyze/{analysis_id}/recommendation
```

It no longer invokes OpenAI.

## Frontend polling

The frontend uses request-completion-driven `setTimeout` behavior rather than `setInterval`, preventing overlapping status requests. Suggested intervals come from the server:

| State | Default interval |
|---|---:|
| queued | 2 seconds |
| predicting_local | 2 seconds |
| analyzing_regions | 3 seconds |
| recommendation queued/processing | 5 seconds |
| terminal state | polling stops |

Transient network failures use exponential backoff up to 15 seconds. An `AbortController` cancels the previous polling loop when a new analysis begins, a saved result is loaded, or the analysis hook resets.

The former six-attempt recommendation loop was removed. It called the work-producing endpoint repeatedly and could duplicate expensive OpenAI operations. The new flow creates a job once and polls read-only status.

## Loading UI

New or refreshed jobs display an animated spinner and status-specific copy for upload, queueing, local prediction, and facial-region analysis. Queue position is shown when available. The existing face scanning animation remains available when the just-selected image preview is still in browser memory.

After analysis becomes ready, the dashboard is displayed immediately. Recommendation cards independently show their spinner for `queued`, `processing`, or `fallback_processing`; the rest of the analysis remains usable.

Animations include `role="status"`, `aria-live`, and reduced-motion behavior.

## Guest refresh and history behavior

The canonical result route remains:

```text
/analyze/{analysis_id}
```

It is no longer a frontend-protected route. A guest can refresh or reopen an anonymous analysis link, resume polling, and load its persisted recommendation without authenticating. `/history`, account, and profile behavior remains authenticated.

If an expired local login token exists while opening a guest result, the frontend clears the invalid token and continues loading the result instead of redirecting to the landing page.

Backend ownership rules remain:

- anonymous analyses (`user_id IS NULL`) are readable with their unguessable link;
- account-owned analyses require the matching authenticated user;
- the history-list endpoint remains authenticated and does not enumerate anonymous analyses.

Analysis identifiers were increased from approximately 32 random bits to 128 random bits because an anonymous result URL acts as a bearer link.

## Deployment notes

- Run exactly one Uvicorn worker for this local presentation architecture.
- Use a named Cloudflare Tunnel if the QR code must remain stable.
- Serve frontend and API through the same HTTPS hostname when possible.
- Keep `.runtime/uploads` mounted and ensure it has sufficient disk space.
- The queue and results are database-backed, but worker execution is in-process; restarting the app pauses work until recovery requeues stale jobs.
- Product and analysis workers share the same OpenAI project limits even though their application concurrency controls are separate.
